### Slice 1.5 - Webhook receiver

1. `POST /webhooks/paypal` reads the body straight from the servlet input stream as bytes; no Spring message converter parses it first. Body limit: 1 MiB.

3. The event envelope is parsed only after `verification_status = SUCCESS`. Unverified requests return `400` with RFC 7807 `code=WEBHOOK_VERIFICATION_FAILED` and persist nothing.
4. `webhook_events` Flyway migration: `event_id` TEXT PK, `event_type`, `raw_body` JSONB, `received_at`, `processed_at`, plus a partial index for unprocessed events.
5. The raw event is inserted before application. Duplicate processed event -> `200` no-op; duplicate unprocessed event -> retried. This covers a crash between persistence and application.
6. Webhook verification failures at PayPal return `503`, allowing PayPal to retry; adapter logs `PayPal-Debug-Id` on every HTTP error.
7. Baseline Spring Security permits `/webhooks/paypal` and actuator health/info, and exempts the webhook POST from CSRF. Every other route stays authenticated.
8. Event application is behind `PaymentEventApplier`. No production applier exists until the payment entity and state machine land in Phase 2; verified events are stored with `processed_at = NULL` in the meantime.
9. Exact Payouts event names recorded in ADR `003-webhook-raw-body-verification.md` (source: PayPal webhook event-name reference, read 2026-11-11).

### Slice 2.1 - Pure policy engine

1. `com.leash.policy` contains no Spring, JPA, or I/O imports. `PolicyEngine` is constructed with the platform hard cap and `evaluate(PolicyContext)` is deterministic.
2. Fixed rule order: agent active, USD supported, positive amount, hard cap, normalized payee allow-list, weekly budget. All violations are collected; the first reason is primary.
3. Outcome: any violation -> `DENY`; otherwise amount at or below the auto-approve threshold -> `APPROVE`; above it -> `ESCALATE`.
4. `BudgetPeriod` is a half-open UTC Monday-to-Monday window derived from the injected `Clock`; the decision records the window it evaluated.
5. Budget rule is `spent + reserved + amount <= weeklyLimitMinor`. Pending approvals reserve budget. Arithmetic saturates instead of overflowing.
6. `AgentPolicy` normalizes allow-list emails (trim + lower-case) at construction; request payees are normalized the same way. Null or blank payees fail closed with `PAYEE_NOT_ALLOWED`.
7. `PolicyDecision` enforces its invariants: `DENY` always has reasons; `APPROVE`/`ESCALATE` never do.
8. `PolicyConfiguration` wires the single `PolicyEngine` bean from `leash.max-payment-minor`.
9. Tests: **42** policy tests (35 engine + 7 budget-period), covering each rule, cap/limit/threshold boundaries, multi-violation ordering, Monday midnight and year rollover, overflow, and input validation.

### Slice 2.2 - Pure payment state machine

1. `PaymentStateMachine` is the only place transitions happen; pure Java with no Spring or JPA imports.
2. Transition table exactly per `AGENTS.md` 7.2: `PENDING_APPROVAL -> APPROVED | REJECTED`, `APPROVED -> SUBMITTED | FAILED`, `SUBMITTED -> SUCCEEDED | FAILED`; `SUCCEEDED`, `FAILED`, `REJECTED`, and `DENIED` are terminal.
3. Illegal transitions throw `IllegalStateTransitionException` carrying the source and target states.
4. `canTransition`, `allowedTargets`, and `isTerminal` support idempotent callers; exposed target sets are immutable.
5. Webhook handlers must gate on the current state being `SUBMITTED`. `APPROVED -> FAILED` exists for a failed submission, not for a webhook.
6. Tests: **55** state-machine tests, including an exhaustive 49-pair matrix (7 states x 7 states), terminal immutability, null handling, and the success-before-submission rule.

### Slice 2.3 - Agents, hashed API keys, policies, API-key auth

Flyway `V3__agents_policies_api_keys.sql`: `agents`, `policies`, `policy_payees`, and `api_keys`, with `CHECK` constraints for non-blank names, valid statuses, non-negative limits, USD-only currency, normalized payee emails, 64-character hashes, and 8-character prefixes. Indexes on `api_keys(prefix)` and `api_keys(agent_id)`.

### Slice 2.4 - Append-only ledger

1. Flyway `V4__ledger_events.sql`: `ledger_events` with `agent_id`, nullable `payment_id`, `event_type`, `actor`, JSONB `payload`, and `created_at`; checks for non-blank type/actor and object-shaped payloads; indexes for agent timeline, payment timeline, and recent events.
2. Database triggers reject `UPDATE`, `DELETE`, and `TRUNCATE` with an "append-only" error. The Java store exposes only insert and read.
3. **No foreign keys** on `agent_id` or `payment_id`: an immutable audit trail must survive agent/payment deletion and must not block it. Referential integrity is the application's responsibility (ADR `004-append-only-ledger.md`).
4. `LedgerService.append` uses `Propagation.MANDATORY`, so the business change and its ledger fact commit or roll back together; calling it outside a transaction fails immediately.
5. `LedgerEventType` covers the documented facts: payment requested, decision made, approval created/decided, PayPal submitted/status changed, reconciled, policy changed, agent status changed, key rotated.
6. `LedgerPayloadGuard` rejects forbidden field names (tokens, secrets, passwords, key hashes) and values resembling agent API keys, bearer tokens, or private keys. Errors name the path, never the value.
7. `LedgerEvent` is immutable, keeps payload insertion order, and its `toString()` omits the payload so accidental logging cannot leak data.

Tests: **14** Testcontainers integration tests: insert/read round trip, generated id, fixed clock timestamp, JSONB values, unknown payment, UPDATE/DELETE/TRUNCATE rejection, forbidden and nested secret fields, key/bearer/private-key values, unsupported types, null values, caller-transaction requirement, argument validation, and `toString` redaction.

### Slice 2.5 - Payment gateway with idempotency and locking

1. Flyway `V5__payment_requests_approvals.sql`: `payment_requests` (canonical fields, decision, PayPal ids, version, and the stored budget snapshot) and `approvals`. `CHECK` constraints enforce positive amounts, a three-letter currency, a 64-character fingerprint, valid states/outcomes, `DENY`-has-reason and non-`DENY`-has-no-reason, `DENY` persisted as `DENIED`, and non-negative budget values. Unique `(agent_id, idempotency_key)`; indexes for agent timeline, state scans, and PayPal batch lookup.
2. `PaymentCommand` normalizes the email (trim/lower-case), currency (trim/upper-case), and memo (strip; null becomes empty) before validation. `PaymentFingerprint` hashes the length-prefixed canonical fields in the fixed order `payeeEmail`, `amountMinor`, `currency`, `memo`; length prefixes prevent field-boundary collisions.
3. `IdempotencyKeys` requires 1-128 characters from `A-Z a-z 0-9 . _ : -`. Missing header -> `400 IDEMPOTENCY_KEY_REQUIRED`; malformed header -> `400 INVALID_IDEMPOTENCY_KEY`.
4. **TX-A** (`PaymentTransactionService.prepare`): `SELECT ... FOR UPDATE` on the agent row, idempotency lookup, budget aggregates computed **inside the lock**, pure `PolicyEngine`, then insert the payment, an approval row for `ESCALATE`, and the ledger facts. The transaction commits before PayPal is contacted.
5. Identical key + identical fingerprint returns the stored record with `Idempotent-Replayed: true` and makes no PayPal call. Same key + different fingerprint -> `422 IDEMPOTENCY_KEY_REUSED`. Two concurrent same-key requests produce one row and one payout.
6. `JdbcPaymentStore.budgetTotals` implements `spent = APPROVED + SUBMITTED + SUCCEEDED`, `reserved = PENDING_APPROVAL` for the current UTC week. `DENIED`, `REJECTED`, and `FAILED` release their amount.
7. **TX-B** records PayPal identifiers and moves `APPROVED -> SUBMITTED`. Optimistic locking is explicit SQL (`WHERE id = ? AND version = ?`); zero rows raises `OptimisticLockingFailureException`.
8. PayPal failures: no status, timeouts, `429`, or `5xx` leave the payment `APPROVED` for the reconciler; a definitive `4xx` (except `429`) moves it to `FAILED`, writes `raw_status=SUBMISSION_FAILED`, and releases budget. `PaymentGatewayService` never calls PayPal inside a transaction.
9. `POST /api/v1/payments` returns `201` for `APPROVE` (usually `SUBMITTED`), `ESCALATE` (`PENDING_APPROVAL`), and `DENY` (`DENIED`). RFC 7807 errors carry `code`, `details`, and `correlationId`.
10. Ledger facts: `PAYMENT_REQUESTED` (actor `agent`), `DECISION_MADE` (actor `policy-engine`), `APPROVAL_CREATED`, `PAYPAL_SUBMITTED` and `PAYPAL_STATUS_CHANGED` (actor `paypal-adapter`). The API key is never written to a payload or echoed in a response.
11. Tests: **73** new (46 unit + 27 integration). Integration coverage: threshold approve, escalation + approval row, unknown payee, weekly budget, unsupported currency, multi-violation ordering, replay identity, `422` reuse, missing/malformed key, five validation cases, transient `500`/`503`/`429`/timeout, permanent `400`/`404`/`422` plus budget release, TX-A committed before PayPal, same-key concurrency, and a five-thread budget race that approved exactly two of five `$20.00` requests against `$50.00`.

### Slice 2.6 - Reconciler, payment read, live budget

1. `ReconcilerProperties` (`leash.reconciler.*`) configures `enabled` (default `true`), `interval` (default `30s`), `approved-retry-after` (default `60s`), `submitted-poll-after` (default `10m`), and `batch-size` (default `100`). `PaymentConfiguration` enables scheduling; `application.yml` exposes each value as an environment variable.
2. `PaymentReconciler.reconcileOnce()` finds stale `APPROVED` rows with `findStaleByState(...)` and resubmits through `PaymentGatewayService.retryApproved`. The same payment id is the PayPal idempotency key, so a crash-repair retry cannot create a second payout.
3. Stale `SUBMITTED` rows are polled through `PayPalPayoutsClient.lookup`, then applied with `PaymentTransactionService.applyReconciledStatus`. Only `SUBMITTED` can move; a terminal state is never regressed by a late or contradictory PayPal status.
4. A poll that stays `SUBMITTED` refreshes `raw_status` and `updated_at`, so the next poll waits another full ten minutes instead of hot-looping every scheduler tick.
5. Every repair writes a `RECONCILED` ledger event with actor `reconciler` and payload keys `action` (`RETRY_SUBMIT`, `RETRY_SUBMIT_FAILED`, `POLL`), `previousState`, `state`, batch/item raw statuses, and HTTP status where relevant. Normal direct submissions keep their existing `paypal-adapter` actors.
6. Network calls happen outside transactions, mirroring the committed-before-PayPal rule. Per-row failures are isolated and counted; one PayPal failure does not abort the rest of the pass. `OptimisticLockingFailureException` is logged at INFO and retried on a later pass.
7. `GET /api/v1/payments/{id}` returns the stored payment to its owning agent and returns the same `404 PAYMENT_NOT_FOUND` for a missing payment or another agent's payment, so ids cannot be probed. `GET /api/v1/budget` returns live `limitMinor`, `spentMinor`, `reservedMinor`, and `remainingMinor` for the current UTC week.
8. `AgentStore.findAgent` reads the agent, policy, and payees without `FOR UPDATE`; budget reads do not block payment decisions. `AgentStore.lockAgent` remains the only lock path for the payment decision itself.
9. Path values that are not UUIDs return `400 INVALID_PATH_VALUE` as RFC 7807; a valid but unknown id returns `404 PAYMENT_NOT_FOUND`.
10. The scheduled entry point checks `leash.reconciler.enabled`. Tests set it to `false` globally and call `reconcileOnce()` explicitly with a mutable `MutableClock`, so background scheduling can never race a test.
11. Tests: **13** new (7 reconciler integration + 6 gateway/read integration). Coverage: crash repair with exactly one payout, stale success, stale failure with budget release, pending poll plus poll-clock refresh, no poll before ten minutes, permanent retry failure, disabled scheduler entry point, owned payment read, other-agent and unknown-payment `404`, auth required, live budget, and budget release on permanent failure.

### Slice 2.7 - Webhooks drive the payment state machine

1. `PayPalPayoutItemEventApplier` is the production `PaymentEventApplier`. Verified events now move payments instead of being stored unprocessed. The receiver still persists first, applies second, and marks `processed_at` last.
2. `PayoutItemWebhookParser` reads the real Payouts shape (`resource.payout_item.sender_item_id`) and accepts the flat `resource.sender_item_id` fallback. It prefers `resource.transaction_status` and falls back to the event-type suffix when the status field is absent.
3. Only `PAYMENT.PAYOUTS-ITEM.*` events are candidates. Batch events (`PAYMENT.PAYOUTSBATCH.*`), unrelated events, malformed JSON, non-UUID sender ids, and missing sender ids are acknowledged and marked processed without touching a payment, so they cannot cause a retry loop.
4. `PaymentTransactionService.applyPayoutItemWebhook` re-reads the payment inside the transaction, requires the current state to be `SUBMITTED`, maps through `PayPalStatusMapper`, and uses the guarded version update. A late event for a terminal payment is acknowledged but writes no ledger fact.
5. `SUCCESS` moves `SUBMITTED -> SUCCEEDED`; `FAILED`, `BLOCKED`, `RETURNED`, `REFUNDED`, `REVERSED`, and `CANCELED` move it to `FAILED`; `PENDING`, `UNCLAIMED`, `ONHOLD`, `HELD`, and unknown statuses keep it `SUBMITTED` while refreshing `raw_status` and `updated_at`. `CANCELED` and `HELD` were added to the item mapping because PayPal's event-name reference includes them even though the Payouts OpenAPI item list does not.
6. A webhook that arrives while the payment is still `APPROVED` is a race with TX-B. The applier throws, the receiver returns `500`, the event stays unprocessed, and PayPal's redelivery applies it after submission. The test exercises the full path: crash -> `APPROVED` -> webhook rejected -> reconciler submits -> same event id replayed -> `SUCCEEDED`.
7. Every applied event writes one `PAYPAL_STATUS_CHANGED` ledger fact with actor `paypal-webhook` and payload `previousState`, `state`, `payoutBatchId`, `rawItemStatus`, and `eventType`. Duplicate event ids are deduped before the applier and produce no second fact.
8. Tests: **18** new (7 parser + 9 webhook integration + 2 mapper cases). Integration coverage: item success, item failure with budget release, pending item refresh, duplicate event id, late failure after success, late success after failure, batch event ignored, unknown payment acknowledged, and the pre-submission retry race.

### Slice 3.1 - Admin security chain, CSRF, agents/policy/kill switch

1. `AdminProperties` (`leash.admin.username`, `leash.admin.password-hash`) requires `ADMIN_USERNAME` and a BCrypt `ADMIN_PASSWORD_HASH`. There is **no default credential**: startup fails when either is missing, and only a hash is accepted, so the plaintext password never lives in configuration or logs.
2. Two ordered `SecurityFilterChain` beans. `@Order(1)` matches `/api/v1/admin/**` and uses an in-memory `DaoAuthenticationProvider` with BCrypt and HTTP Basic. `@Order(2)` keeps the stateless agent-key chain. The agent filter never runs on an admin route, and the admin chain never consults an API key, so a valid `lsh_...` key cannot reach administration even though both chains live in one application.
3. Admin CSRF uses `csrf.spa()` (readable `XSRF-TOKEN` cookie plus the SPA request handler). A `CsrfCookieFilter` forces the lazily generated token, so even the first admin `GET` carries the cookie the console must mirror in `X-XSRF-TOKEN` on writes. A write without a matching token returns `403 INVALID_CSRF_TOKEN`; a CSRF failure is distinguished from an ordinary access denial.
4. Admin errors are RFC 7807. Unauthenticated requests return `401 UNAUTHORIZED` with `WWW-Authenticate: Basic realm="leash-admin", charset="UTF-8"`. Validation keeps the global `VALIDATION_FAILED` shape; an unknown agent id returns `404 AGENT_NOT_FOUND` from a dedicated, highest-precedence advice.
5. `AdminAgentController` exposes the six contract routes: `POST /api/v1/admin/agents` (201, plaintext key returned once), `GET /api/v1/admin/agents`, `PUT /api/v1/admin/agents/{id}/policy`, `POST .../suspend`, `POST .../resume`, and `POST .../rotate-key`. Response DTOs never carry a key except create and rotate, and their `toString()` redacts it.
6. Every admin mutation locks the agent row first (`SELECT ... FOR UPDATE`) and appends its ledger fact in the same transaction. This is the same lock the payment decision takes, so a policy edit cannot land between a decision's agent snapshot and its budget check.
7. Ledger payloads are self-contained before/after facts: `POLICY_CHANGED` carries previous and new weekly limit, threshold, and allow-list; `AGENT_STATUS_CHANGED` carries previous and new status; `API_KEY_ROTATED` carries only the new 8-character prefix and the number of revoked keys. Suspend and resume are idempotent and write no event when the status is unchanged.
8. Key rotation revokes every active key and inserts the replacement inside the agent lock. The old key fails immediately with `401 INVALID_API_KEY`; the new key authenticates on the agent API.
9. The admin agent list computes budgets with one grouped query (`budgetTotalsByAgent`) for the current UTC week, then maps `spent`, `reserved`, and `remaining`. Missing agents default to zero, so the endpoint never issues a query per agent. `remainingMinor` saturates at zero.
10. `AgentStore` gained `listAgents`, `updatePolicy`, `updateStatus`, and `revokeActiveApiKeys`. The new `AgentBudgetReader` port is implemented by `PaymentAgentBudgetReader` in the payment feature, keeping the dependency direction inward.
11. ### Slice 3.2 - Approval workflow

1. `ApprovalRecord` models the persisted row (`PENDING`/`APPROVED`/`REJECTED`, requested time, decided time/by/note, version) and enforces the same invariant as the database: a decided approval names who decided it and when; a pending one carries neither. `PendingApproval` joins the approval with its payment so `GET /api/v1/admin/approvals` needs exactly one query and never an N+1.
2. `ApprovalService` owns the use case; `PaymentTransactionService.decideApproval` owns the transaction. The agent row is locked first (`SELECT ... FOR UPDATE`), then the approval and payment are re-read. This serializes approval decisions with policy edits and payment decisions for the same agent.
3. A decision is a compare-and-set: `UPDATE approvals ... WHERE id = ? AND version = ? AND status = 'PENDING'`, followed by a guarded payment transition in the same transaction. A racing caller that loses the version check re-reads the winner: the same decision is a no-op (`replayed = true`), the opposite decision is `409 APPROVAL_ALREADY_DECIDED`. Exactly one `APPROVAL_DECIDED` fact is written.
4. Approve re-runs the **full** policy engine, not a subset. The budget totals for the current UTC week have this payment's own reservation removed (`BudgetTotals.minusReserved`), because the row is still `PENDING_APPROVAL` at check time. If the payment was created in an earlier week, its reservation is not in the current window and is not subtracted; the re-check evaluates the amount against the current week.
5. Any `DENY` from the re-check auto-rejects: approval `REJECTED`, payment `REJECTED`, ledger reason `HARD_RULE_VIOLATION`, and the ordered policy reasons in the payload. The API returns `200` with `autoRejected = true` and `rejectionReasons`, because the admin's request was handled; it is not an error. Suspended agent, removed payee, and lowered weekly limit are each covered by a test.
6. An accepted approve commits `APPROVED` before PayPal is contacted. `PaymentGatewayService.submitApproved` then runs outside the transaction and reuses the existing TX-B submission path. A transient PayPal failure leaves the payment `APPROVED` for the reconciler; a definitive rejection marks it `FAILED`.
7. Reject moves both rows to `REJECTED`; no money moves and the reservation is released automatically because budgets are derived from payment state. A later approve is a `409`.
8. Repeats are idempotent: a second approve returns `200` with `replayed = true`, the original note, the current payment state, and **no second PayPal call** and no second ledger fact.
9. Ledger payload for every decision: `approvalId`, `decision`, `reason` (`HUMAN_APPROVAL`, `HUMAN_REJECTION`, or `HARD_RULE_VIOLATION`), `previousState`, `state`, optional `note`, and `policyReasons` only for an automatic rejection. Actor is the authenticated admin username.
10. Errors are RFC 7807: `404 APPROVAL_NOT_FOUND` and `409 APPROVAL_ALREADY_DECIDED`. Notes are capped at 500 characters at the boundary and in the service. Agent keys cannot reach the queue, and writes require the CSRF token.
11. Tests: **12** new Testcontainers/MockMvc integration tests: approve submits and ledgers with the live budget moving from reserved to spent, double approve is a no-op, reject releases the reservation and blocks a later approve, approve-versus-reject has exactly one 200 and one 409 with one ledger fact, the three auto-reject re-checks, a transient PayPal failure leaving `APPROVED`, unknown ids, agent-key isolation, missing CSRF, oversized note, and the pending queue shape.

### Slice 3.3 - Admin payment ledger, timeline, manual refresh

1. `GET /api/v1/admin/payments` returns a page envelope: `content`, `page`, `size`, `totalElements`, `totalPages`. `page` is zero-based and defaults to 0; `size` defaults to 25 and is capped at 100. Out-of-range paging and an inverted window return `400 INVALID_QUERY` with a precise detail.
2. Filters are `status`, `agentId`, `from`, and `to`. `from` is inclusive and `to` is exclusive, so adjacent windows never overlap. Time filters accept ISO-8601 instants, keeping the UTC week boundary unambiguous. The SQL is assembled from fixed fragments with bound parameters; no user value reaches the statement text.
3. Ordering is `created_at DESC, id DESC`, so equal timestamps still produce a stable page. The page query joins `agents` to select `agent_name`; the list is exactly **two SQL statements** per request (page plus count) for every page size and filter combination. A test-scoped counting `JdbcTemplate` asserts this.
4. `AdminPaymentResponse` is a DTO record: payment id, agent id/name, payee, amount and currency, memo, state, decision outcome and reasons, PayPal batch id, raw status, and timestamps. Entities never leave the service. The stored decision-time budget snapshot is deliberately not repeated here.
5. `GET /api/v1/admin/payments/{id}/events` returns the append-only ledger timeline oldest first, with event id, type, actor, payload, and timestamp. It reuses `LedgerService.eventsForPayment`; an unknown payment is `404 PAYMENT_NOT_FOUND`.
6. `POST /api/v1/admin/payments/{id}/refresh` polls PayPal once for a `SUBMITTED` payment with a batch id. The lookup happens outside every transaction; the result is applied through `PaymentTransactionService.applyReconciledStatus`, the same guarded path the reconciler uses. A poll that stays `SUBMITTED` refreshes the raw status and `updated_at`; a terminal row is immutable.
7. Refresh is a deliberate no-op for anything that is not `SUBMITTED` with a batch id. It returns `200` with `refreshed = false` and a reason (for example, "Only SUBMITTED payments can be polled"), and it never resubmits or moves a terminal payment. A PayPal lookup failure returns `502 PAYPAL_UNAVAILABLE` and leaves the payment unchanged.
8. The admin payment routes stay on the admin chain: an agent key receives `401 UNAUTHORIZED`, and refresh without the `X-XSRF-TOKEN` header receives `403 INVALID_CSRF_TOKEN`.
9. `PaymentExceptionHandler` now maps `InvalidPaymentQueryException` to `400 INVALID_QUERY`, `PayPalPayoutException` to `502 PAYPAL_UNAVAILABLE`, and uses a generic payment-not-found detail that is accurate on both the agent and admin routes.

## Findings that affect later slices

1. **Spring Boot 4 renamed/split modules.** Use `spring-boot-starter-webmvc` and `spring-boot-starter-flyway`, per-starter `-test` artifacts, Jackson 3 (`tools.jackson`), JUnit 6. This differs from most Boot 3 examples; verify APIs against the installed version.
2. **No auto-configured `RestClient.Builder`** with the web starter in Boot 4 (HTTP clients are a separate module). The PayPal `RestClient` is built directly in `PayPalConfiguration`.
3. **WireMock 3.13.2 main artifact is incompatible with Boot 4's Jetty 12 dependency management** (WireMock 3.x expects Jetty 11). Use `org.wiremock:wiremock-standalone:3.13.2` (shaded, test scope).
4. **PostgreSQL rejects the Windows JVM zone `Asia/Calcutta`.** The app pins the JVM default to UTC in `main()` and Surefire runs with `-Duser.timezone=UTC`.
5. **Payout batch `SUCCESS` is not payment success.** PayPal's batch status only means processing finished; items can still be `ONHOLD` or `UNCLAIMED`. `PayPalStatusMapper` prefers the item status and fails safe to `SUBMITTED` on unknown values (ADR `002-payout-status-mapping.md`).
6. **PayPal's current Payouts OpenAPI is authoritative for field names.** Source used: `paypal/paypal-rest-api-specifications` -> `openapi/payments_payouts_batch_v1.json` (OpenAPI 3.0.3). Endpoint: `POST /v1/payments/payouts`; lookup: `GET /v1/payments/payouts/{id}`.
7. **Webhook signatures cover bytes, not objects.** The verification request must contain the original event JSON text. The receiver reads bytes directly and splices them into the verification body; tests compare the full request body (ADR `003-webhook-raw-body-verification.md`).
8. **Boot 4's security test annotation moved** to `org.springframework.boot.webmvc.test.autoconfigure.AutoConfigureMockMvc` (the old `org.springframework.boot.test.autoconfigure.web.servlet` package does not exist in 4.1.2).
9. **Webhook application is intentionally deferred.** `PaymentEventApplier` is optional; with no bean, events remain stored and unprocessed. Phase 2 must add the real applier and a replay path for rows with `processed_at IS NULL`.
10. **JaCoCo is not version-managed by Boot 4.1.2.** The build pins `jacoco-maven-plugin` 0.8.13 and passes its agent through the `jacoco.argLine` property so the UTC Surefire flag survives. The coverage check is scoped to `com/leash/policy/**`.
11. **`HttpServletRequest.getServletPath()` can be empty.** Both MockMvc and Boot's servlet mapping can leave it blank, which silently skipped the agent key filter. The filter derives its route from `getRequestURI()` minus `getContextPath()` instead.
12. **Audit logs must not depend on their subjects.** `ledger_events` intentionally has no foreign keys; cascading deletes would erase history and restrictive keys would block deletion. Add only application-level validation (ADR `004-append-only-ledger.md`).
13. **The payment response `budget` is a decision-time snapshot.** It is stored with the payment so an idempotent replay returns an identical body. A later permanent submission failure sets the live state to `FAILED` and releases the amount, but the create response still shows the snapshot. `GET /api/v1/budget` is the live balance.
14. **Bean Validation is stricter than domain normalization.** Padding an email or currency is rejected with `400` at the boundary; the domain still trims and cases values as defense in depth. Do not rely on the domain normalizer to make malformed API input acceptable.
15. **Replaying a stuck `APPROVED` payment does not retry PayPal.** The replay contract returns the stored response. The reconciler owns retries for `APPROVED` rows and reuses the same `PayPal-Request-Id`, so the retry cannot duplicate the payout.
16. **Optimistic locking is explicit SQL, not `@Version`.** `payment_requests.version` increments only on the guarded update; a zero-row update raises `OptimisticLockingFailureException`. Keeping this in JDBC avoids mixing JPA entities into the payment flow.
17. **Phase 3 policy edits must take the same agent row lock.** `lockAgent` reads the agent and its policy after `SELECT ... FOR UPDATE`; an admin policy update that does not lock the agent row could let a decision straddle an old agent snapshot and a new policy snapshot under READ COMMITTED. Lock the agent row first in the policy-edit transaction.
18. **Reconciler thresholds are relative to `updated_at`, not to the scheduler tick.** An `APPROVED` row is retried once it is older than 60 s; a `SUBMITTED` row is polled once it is older than 10 min. A pass that finds nothing is a cheap indexed read, so the 30 s interval does not need to match either threshold.
19. **A poll that stays `SUBMITTED` must touch `updated_at`.** Without the refresh, the same stale row would be polled on every scheduler tick. Refreshing the timestamp turns the ten-minute threshold into a per-payment poll interval and prevents a PayPal query storm.
20. **Budget reads use a non-locking agent read.** `AgentStore.findAgent` deliberately has no `FOR UPDATE`; a budget read must not queue behind payment decisions. Only the decision path (`lockAgent`) serializes budget checks, so the lock ordering stays one-way.
21. **The scheduled reconciler is disabled in tests.** `src/test/resources/application.properties` sets `leash.reconciler.enabled=false`; tests invoke `reconcileOnce()` directly after moving a `MutableClock`. This keeps the suite deterministic and avoids a background pass mutating rows between assertions.
22. **Reconciler repairs are regular ledger facts.** `RECONCILED` is append-only like every other event and records the action, previous state, new state, raw PayPal statuses, and HTTP status. A retry that succeeds writes `PAYPAL_SUBMITTED` plus `RECONCILED`; a retry rejected outright writes `PAYPAL_STATUS_CHANGED` plus `RECONCILED`.
23. **Webhook item events, not batch events, move payments.** A batch `SUCCESS` only means processing finished. `PAYMENT.PAYOUTSBATCH.*` deliveries are acknowledged and marked processed but cannot change a payment.
24. **Webhook handling can race TX-B.** The payment row is committed as `APPROVED` before PayPal is called; a very fast webhook can arrive before TX-B stores the batch id. The applier treats `APPROVED` as retryable and leaves the event unprocessed, so PayPal's redelivery applies the status after submission.
25. **The terminal-state guard belongs in the transaction.** Dedupe by event id is not enough: PayPal can send a later event with a new id. The applier re-reads the row under the transaction, requires `SUBMITTED`, and writes no ledger fact for a terminal payment.
26. **Unusable item events are acknowledged, not retried.** Missing or non-UUID `sender_item_id`, malformed resources, and unrelated event types are marked processed. Retrying them forever would block the queue without any chance of success.
27. **Unknown item statuses fail safe.** An unknown `transaction_status` stays `SUBMITTED` and refreshes the raw status, leaving the reconciler to keep polling instead of guessing a terminal outcome.
28. **PayPal event names outrun the OpenAPI item list.** `CANCELED` and `HELD` appear in the webhook event-name reference but not in the Payouts item status enum, so the mapper handles them explicitly (`FAILED` and `SUBMITTED` respectively).
29. **HTTP Basic plus cookie CSRF is a per-request flow.** Every admin request re-authenticates; the CSRF token is not in a session but in a readable cookie. A client must first issue a GET to receive `XSRF-TOKEN`, then mirror it in `X-XSRF-TOKEN`. `csrf.spa()` resolves the plain token from the header and reserves the XOR form for parameter-based submissions.
30. **Admin isolation is by filter-chain path, not by authentication type.** `/api/v1/admin/**` is matched before the agent chain, so the agent filter never executes there. Do not collapse the chains: a single chain would let a valid agent key reach an administrative route.
31. **Admin policy edits must take the agent lock.** The edit, suspend/resume, and rotation all `SELECT ... FOR UPDATE` the agent row. Without it, a payment decision could read the old policy while the new policy commits under READ COMMITTED.
32. **No default admin credential is intentional.** `ADMIN_USERNAME` and a valid BCrypt `ADMIN_PASSWORD_HASH` are mandatory; the application fails fast otherwise. Test credentials live only in `src/test/resources/application.properties`.
33. **The CSRF cookie is lazy.** `CookieCsrfTokenRepository` generates on demand, so a plain GET would not emit `XSRF-TOKEN`. `CsrfCookieFilter` forces `getToken()` after `CsrfFilter`; without it the console's first write would always fail.
34. **Admin budget listing is one grouped query.** `budgetTotalsByAgent` aggregates the whole week in SQL and the service maps missing agents to zero. Adding per-agent queries to the admin list would introduce an N+1 that AGENTS.md 22 forbids.
35. **Approval decisions use the agent lock, not an approval lock.** Locking the agent first gives one consistent lock order across payment creation, policy edits, and approval decisions. Re-reading the approval after the lock turns a race into a simple same-decision no-op or opposite-decision conflict.
36. **The approve re-check must subtract its own reservation.** The payment is still `PENDING_APPROVAL` while the policy engine runs, so leaving its amount in `reserved` would double-count the payment and reject valid approvals at the budget boundary. `BudgetTotals.minusReserved` is floored at zero. If the payment was created in an earlier UTC week, the reservation is not part of the current aggregates and is not subtracted.
37. **An automatic rejection is a successful request.** The API returns `200` with `autoRejected = true` and the policy reasons, not `409` or `422`: the admin asked for a decision and the system made one. A later approve is then an opposite-decision conflict.
38. **A repeated approve must not resubmit.** Idempotent replay returns the current state without calling PayPal, even when a previous submission failed transiently and left the payment `APPROVED`. The reconciler owns that retry, which keeps the "one user click, at most one submission attempt" property and avoids surprising duplicate side effects.
39. **The admin list is two statements, always.** The page query joins `agents` for the display name and the count query reuses the same predicates; neither one loops. This is verified by counting prepared statements through a test-only `JdbcTemplate` subclass, not by trusting the service structure.
40. **Spring 7 `JdbcTemplate` bypasses the public two-argument `execute` for queries.** The internal `query(psc, pss, rse)` path calls a private executor. A counting test hook must override the three-argument `query` (and `execute(String, ...)` for writes) or it will silently count zero.
41. **Manual refresh is a poll, not a retry.** Only `SUBMITTED` rows with a PayPal batch id are usable. Anything else is a `200` no-op with a reason. Letting refresh resubmit an `APPROVED` row would duplicate the reconciler's job and could produce surprising side effects from a button click.
42. **Time filters are instants, half-open.** `from` is inclusive and `to` is exclusive. A page sorted by `created_at DESC, id DESC` is stable even when several payments share the same timestamp, which happens in tests and in fast demo runs.
43. **The CSRF token is the readable cookie value.** Spring Security 7.1 `csrf.spa()` with a cookie repository accepts the raw `XSRF-TOKEN` value as `X-XSRF-TOKEN`; both MockMvc and a live curl probe confirmed it. The console does not need a token endpoint, and it retries once if a cookie was cleared mid-session.
44. **Admin credentials stay in memory.** Persisting the Basic header in `localStorage` would leave a durable secret on disk. The console signs in per page load, which is acceptable for an operator tool and keeps the demo's test credential out of browser storage.
45. **The Vite proxy is part of the auth design.** A cross-origin dev server would make the XSRF cookie third-party and force CORS plus credential handling. Proxying `/api` and `/actuator` keeps the double-submit cookie first-party.
46. **Missing PayPal credentials are a transient submission failure, not a request error.** `PayPalOAuthClient` throws `PayPalOAuthException`; the Payouts adapter wraps it as `PayPalPayoutException` with a null HTTP status; the gateway also catches it directly. The decision has already committed as `APPROVED`, so the API returns `201` with the parked state and the reconciler retries later. Never let an OAuth configuration error escape as a `500` after the decision committed.
47. **AG Grid 36 registers modules and themes differently from 32.x.** Call `ModuleRegistry.registerModules([AllCommunityModule])` once, pass a theme object via the `theme` prop, and use `themeQuartz.withPart(colorSchemeDark)` for dark mode. The old `ag-theme-quartz` CSS class approach is gone.
48. **`CellKeyDownEvent` no longer exposes the keyboard event in 36.x.** Enter-to-open uses a native capture-phase `keydown` listener on the grid container and reads the focused row's `row-index` attribute. Do not try to read `event.event.key` from the AG Grid callback.
49. **No-matching-rows text is `localeText.noMatchingRows`.** `overlayNoRowsTemplate` only covers an empty data source, not a non-empty page filtered down to zero rows by the quick filter or a column filter.
50. **Grid filtering is intentionally split-scope.** Status and agent selects are server filters over the whole ledger; quick and column filters only see the current server page. The footer states the visible count and the UI labels the scopes, because silently filtering one page and calling it "the ledger" would be misleading.
51. **Server paging stays custom.** AG Grid's built-in pagination cannot express the backend page envelope (`totalElements`/`totalPages` with zero-based pages) without extra adapters, so Previous/Next and page size live in the panel around the grid.
52. **AG Grid is the bundle.** A single 1,497 kB chunk (426 kB gzip) is acceptable for an operator console; code-splitting the grid is a possible later optimization, not a correctness issue.
53. **The demo seeder rotates the agent key on every demo-profile startup.** Nothing written to disk can stay valid across restarts. The only copy lives in `DemoAgentCredentials` memory for the process lifetime, and the status endpoint deliberately exposes identity but never the key.
54. **Demo profile gating is structural, not a runtime flag.** The controller, seeder, client, and runner are `@Profile("demo")` beans and `demo/invoices.json` is only read there. Outside the profile, `/api/v1/admin/demo/status` is a normal `404`; the console treats that as "hidden", sets `retry: false`, and never shows an error toast.
55. **Boot 4 moved `WebServerInitializedEvent`.** The package is `org.springframework.boot.web.server.context`, not the Boot 3 `org.springframework.boot.web.context`. The event is the reliable way to discover a random test port or a deployed `PORT` without hardcoding the demo base URL.
56. **A class with two constructors needs an explicit `@Autowired`.** `DemoInvoiceLoader` has a production constructor and a test constructor over a `Resource`; Spring cannot choose, so the single-argument constructor is annotated. The alternative (a separate factory) adds indirection for no benefit.
57. **The demo runner is serialized and failure-isolated.** A `ReentrantLock` keeps two admin clicks from interleaving their summaries; stable invoice idempotency keys would make concurrent runs safe, but the report would be unreadable. A failed invoice becomes an error scene and the run continues, so the demo never stops halfway.
58. **The demo client builds its own `RestClient`.** Boot 4's web starter does not auto-configure a `RestClient.Builder`, so the adapter constructs one with the demo timeouts. This mirrors the PayPal adapter and avoids depending on a bean that only exists with the HTTP-client module.
59. **Jackson 3 throws unchecked `JacksonException`.** `ObjectMapper.readValue` failures are runtime exceptions in Jackson 3, so the loader catches `JacksonException` separately from `IOException` and includes `getOriginalMessage()` in the startup error. Catching only `IOException` would miss malformed JSON.
60. **LLM mode is advertised but disabled, not hidden.** The status response lists both modes so the console can explain the capability, while `llmConfigured = false` disables the LLM radio and points at SCRIPTED. Calling the route directly still fails closed with `501 LLM_NOT_CONFIGURED`; a disabled control is convenience, not the security boundary.
61. **Stable idempotency keys make the second demo run a no-op.** `invoice-<id>` is reused exactly, so a rerun replays the original payment ids and leaves spent/reserved unchanged. A demo database that already contains earlier probe rows will show a higher starting budget; the run's own deltas are still the three scenes.
62. **The run summary is built from the agent's viewpoint.** It counts decisions, names denial codes, and reports replays in plain language. It never includes the API key, agent key prefix, or upstream response bodies, so it is safe to project on screen.
63. **The Maven wrapper download is the fragile part of the Docker build.** The wrapper shell script prefers `wget` and exits on the first failure. A transient network error failed the first image build even though the same URL worked seconds later in a one-off container. The Dockerfile retries the dependency-resolution step twice before failing; treat a single `wget: Failed to fetch` as infrastructure, not as a Maven or repository defect.
64. **The production console is served by the jar, not a separate web server.** The Vite build output is copied into `src/main/resources/static`, and Spring Boot's welcome-page mapping serves `index.html` at `/`. `SecurityConfiguration` permits exactly `/`, `/index.html`, `/favicon.svg`, and `/assets/**`; every API route keeps its own rule. The console uses component state rather than client-side routes, so there is no catch-all rewrite. Adding a router later needs a forward controller that does not widen the API permit list.
65. **The browser tooling folder is repo-adjacent and must stay ignored.** `.gstack/` holds a terminal token and browser session logs. The original `.gitignore` excluded only `.gstack/tmp/`, so a first `git add .` would have staged the token. The root ignore now excludes the whole folder. A scratch-repository check confirmed `.env`, `.gstack/`, and `.idea/` stay untracked while `.env.example` is added.

## Assumptions recorded (reconstructed contract)

1. **Canonical admin prefix is `/api/v1/admin/**`.** The plan mentions both `/admin/...` and `/api/v1/admin/...`; standardized for consistency. Demo runner: `POST /api/v1/admin/demo/run`.
2. **Payouts is the only money-movement rail** for the MVP (Slices 1.3-1.6, G1). Checkout/Orders/Invoicing are out of scope.
3. Hard cap default: **$1,000.00** (`LEASH_MAX_PAYMENT_MINOR=100000`); the $900 deny scene fits under it.
4. Budget period: **UTC week starting Monday 00:00:00**.
5. Denial is persisted as a payment with state **`DENIED`** and returned as HTTP **201** with `decision.outcome=DENY`.
6. State set: `PENDING_APPROVAL`, `APPROVED`, `SUBMITTED`, `SUCCEEDED`, `FAILED`, `REJECTED`, `DENIED`.
7. Budget arithmetic: `spent = APPROVED + SUBMITTED + SUCCEEDED`, `reserved = PENDING_APPROVAL`; `DENIED`, `REJECTED`, and `FAILED` release. Rows are scoped by `created_at` to the half-open UTC week.
8. Idempotency fingerprint: SHA-256 over length-prefixed `payeeEmail`, `amountMinor`, `currency`, `memo` in that order, computed after normalization. Replay returns the stored decision-time response.
9. PayPal submission failures: `429`, `5xx`, timeouts, and absent HTTP statuses are transient and leave `APPROVED`; other `4xx` are definitive and move to `FAILED`. The reconciler retries only transient outcomes.
10. The payment create response's `budget` block is the decision-time snapshot, not a live balance.
11. Only `PAYMENT.PAYOUTS-ITEM.*` webhooks can move a payment. Batch events are audit facts, never payment outcomes. The item `transaction_status` is authoritative; unknown values stay `SUBMITTED`.
12. A webhook that arrives before TX-B commits is not dropped: the event stays unprocessed and the delivery is retried after submission.
13. **Admin auth is HTTP Basic with a cookie-backed CSRF token**, not form login. Every browser write must send `X-XSRF-TOKEN` equal to the `XSRF-TOKEN` cookie; non-browser admin calls do the same after a GET.
14. **Admin mutations share the payment decision's agent lock.** Policy edits, status changes, and key rotation serialize with budget checks on the same row.
15. **Approve re-checks the full policy and auto-rejects on any `DENY`.** The check uses budget totals with this payment's reservation removed. The resulting decision is `REJECTED` with ledger reason `HARD_RULE_VIOLATION`; it is returned as a normal `200` response with `autoRejected = true`.
16. **A repeated approval decision is a no-op.** Same decision returns `200` with `replayed = true` and never contacts PayPal again; the opposite decision returns `409 APPROVAL_ALREADY_DECIDED`. Racing decisions are serialized by the agent row lock and the approval version compare-and-set.
17. **Admin paging is zero-based, default 25, maximum 100.** The response carries `content`, `page`, `size`, `totalElements`, and `totalPages`. An empty result has `totalPages = 0`.
18. **Admin time filters are ISO-8601 instants with `from` inclusive and `to` exclusive.** The console can request precise windows without date-to-time-zone conversion on the server.
19. **Manual refresh polls PayPal only.** It applies the outcome through `applyReconciledStatus`; it never resubmits, never moves a terminal payment, and returns `refreshed = false` plus a reason when there is nothing to poll. A PayPal failure is `502 PAYPAL_UNAVAILABLE` and changes nothing.
20. **The console signs in with a credential form, not the browser's Basic challenge.** The form sends `Authorization: Basic ...` on each request and keeps the value in memory. This avoids browser credential caching and gives the operator an explicit sign-out.
21. **The ledger is the console's primary panel.** It is server-paged and refreshed every three seconds; status and agent filters are server-side, while quick and per-column filters apply to the loaded page and the footer says so.
22. **The timeline drawer is read-only except for manual refresh.** Refresh polls PayPal only for `SUBMITTED` payments with a batch id; the drawer shows the disabled reason for every other state.
23. **AG Grid 36 is themed by object, not CSS class.** Light and dark themes come from `themeQuartz` with parameters, shared with the app's theme store so the console and the grid switch together.
24. **Demo data is created by the backend demo seeder, never by a production path.** In the `demo` profile, the seeder creates `Invoice Agent` when absent or aligns its policy, resumes it, and rotates its key when present. The console labels the runner "Demo profile" and hides it entirely when the status route is absent.
25. **The demo agent is identified by its configured name.** Re-provisioning matches the agent by name (default `Invoice Agent`), not by a stored id, so a schema reset or a fresh Render database converges to the same three scenes. A second agent with the same name is not created.
26. **SCRIPTED is the deterministic demo mode.** It makes fixed tool calls in invoice order and is the safety net for the video. LLM mode is not implemented in this build: the route fails closed with `501 LLM_NOT_CONFIGURED` until Slice 2.9 adds the `AgentModelClient` port, provider, model, and key.
27. **The demo runner is serialized and partial-failure tolerant.** Concurrent admin clicks wait for the first run; a failed invoice is reported as an error scene without aborting the remaining invoices.
28. **The console learns about the demo runner from the backend.** A `404` on `/api/v1/admin/demo/status` hides the nav item; `enabled`/`ready` gate the panel; `llmConfigured` disables the LLM choice. There is no frontend environment flag to drift from the server.
29. **A demo run's budget snapshot may start above zero.** Earlier probe or demo rows in the same UTC week are real spend and remain counted. The before/after bars make the run's own reservation and spend visible without pretending the database was reset.
